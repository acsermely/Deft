## Arguments and behaviour

Use `call(method, args)` from `/_deft/v1/bridge.js`. Basics, errors and events: `skill.read name=js-bridge/basics`.

- notification listener (`notifications.listen`, SPECIAL, one app at a time: the user grants it from the app's card on the dashboard, and the same sheet opens Android's Notification access screen for the launcher; until that is on, calls return `os_permission_missing` with message `Notification access`): other apps' notifications, never the launcher's own (so never another FL app's `notify.post`). Event `notifications.posted` `{key, package, appLabel, title, text, subText?, time, category?, ongoing, redacted, actions: [{index, title, reply}]}` when a notification is posted or updated (an update with the same content is not sent again); `title`, `text` and action titles may be null; `time` epoch ms; `reply` true when the action takes typed text. Text is cut to 1000 characters (title, subText, appLabel to 200). `redacted` true means title, text and subText were left out: always for notifications marked secret (`VISIBILITY_SECRET`, by the app or by the user's channel setting), and, while the phone is locked and the user chose to hide sensitive content on the lock screen, for private ones (then the lock-screen version is sent when the app has one). Event `notifications.removed` `{key, reason?}` (`reason`: `click`, `dismissed`, `dismissedAll`, `app`, `listener`, `group`, `snoozed`, `timeout`, `blocked`). Events reach only an open page and are never queued; call `active` when the page opens. With `background` and the manifest trigger `notification`, a posted notification that is not ongoing wakes the background module while the app is closed (payload: the posted event; the usual limit of 60 runs an hour applies). `active` → the same shape for every notification showing now, newest first. `dismiss` `{key}` clears it (Android ignores this for ongoing ones). `reply` `{key, actionIndex, text}` (`actionIndex` a number, `text` 1 to 1000 characters) types `text` into that action's reply field and sends it, as replying from the notification shade does; `invalid_args` "that action takes no reply" otherwise. `open` `{key}` (app on screen only; `needs_foreground` in a background run) does what tapping the notification does. Unknown keys fail with `invalid_args` "no such notification"; `unsupported` "The other app no longer accepts this" when the other app cancelled the action. While the app holds this and Notification access is on, the user sees an ongoing notification "<App> is using: Read all your notifications". Revoking the grant or removing the app stops events at once. Notification contents are never written to the audit log.
- accessibility (`accessibility`, SPECIAL, one app at a time: the user grants it from the app's card on the dashboard, and the same sheet opens Android's Accessibility screen to turn on Deft; until that is on, calls return `os_permission_missing` with message `Accessibility`): read the screen of the app in front and act on it. `windowTree` `{maxDepth?, maxNodes?}` (`maxDepth` 0 to 30, default 30; `maxNodes` 1 to 2000, default 1000) → `{package, truncated, nodes: [{id, parentId?, className, text?, contentDescription?, viewId?, bounds: [left, top, right, bottom], clickable, editable, scrollable, checked?, focused, password}]}` for the active window, parents before children, only nodes visible to the user; `bounds` in screen pixels; `checked` only on checkable nodes; a password field never has `text`; texts cut to 1000 characters. Node ids are strings valid until the next `windowTree` call. `perform` `{nodeId, action, text?}` (`action`: `click`, `longClick`, `setText`, `scrollForward`, `scrollBackward`, `focus`; `text` 0 to 5000 characters, for `setText` only) → `{performed}`; an id from an older tree fails with `invalid_args`, as does a node no longer on screen. `gesture` `{path: [[x, y], …], durationMs?}` (1 to 50 points, screen pixels 0 to 100000; one point is a tap; `durationMs` 1 to 10000, default 200) swipes along the path → `{completed}`. `global` `{action}` (`back`, `home`, `recents`, `notifications`, `quickSettings`, `lockScreen`) → `{performed}`. Event `a11y.event` `{type, package, className?, text?}` (`type`: `viewClicked`, `viewLongClicked`, `viewSelected`, `viewFocused`, `viewTextChanged`, `windowStateChanged`, `notificationStateChanged`, `windowContentChanged`, `viewScrolled`, `viewTextSelectionChanged`, `announcement`, `windowsChanged`; no `text` from password fields), at most 10 a second (content changes and scrolling at most 5 of them); events reach only an open page and are never queued. Android's permission dialogs, the package installer, the VPN dialog, all of Settings, and the launcher's own grant and confirm screens (install consent, confirmations, special access, the dashboard, pickers, "Open with", key unlock, and the home screen while the AI agent panel is open) are never shown to the app: their events are left out, `windowTree` and `perform` fail with `unsupported`, and `gesture` fails with `unsupported` while one is on screen. SystemUI's own dialogs (screen recording consent, USB debugging, USB access) are treated the same: no tree and no acting while one shows. The status bar and notification shade stay usable. Other launcher screens (home, app list, web app pages) are readable like any app. None of the methods needs the app on screen (acting on another app means it is not), and background runs may use them; keep the page running with `foreground` while you leave it. While the app holds this and the switch is on, the user sees an ongoing notification "<App> is using: See and control your screen". Revoking the grant or removing the app stops it at once. Screen contents are never written to the audit log. Android 13+ greys out the switch for a launcher not installed from a store until the user allows restricted settings in the launcher's app info.
- browser role (`role.browser`, SPECIAL, one app at a time; no methods): the user grants it from the app's card on the dashboard, and the same sheet asks Android to make Deft the default browser (on a phone that does not offer this, the sheet says so). From then on, an `http` or `https` link the user opens from another app opens your app and arrives as event `intents.viewReceived` `{type: "url", url, items: []}` (queued until you subscribe; at most 8 KiB, longer or other links are not passed on). The link is data only: your page is never navigated to it and the same-origin rule stays, so show it, fetch it (with `network.open`) or hand it on with `intents.open`. Links the launcher opens itself (outside links in any app, `intents.open`) never come back to you: they go to another browser. Revoking the grant or removing the app turns the launcher's browser entry off, and Android goes back to another browser; the user can also pick another browser in Android Settings under Default apps.
- assistant role (`role.assistant`, SPECIAL, one app at a time; no methods): the user grants it from the app's card on the dashboard, and the same sheet asks Android to make Deft the digital assistant app. Most phones only let the user pick that in Android Settings under Default apps, Digital assistant app; the sheet sends them there, and says so when the phone does not list the launcher. From then on, holding the Home button, the assistant gesture or the assistant button opens your app with event `assist.invoked` `{source}` (queued until you subscribe). `source` is `assist-gesture` when it came from Android's assistant gesture or button, which only the system can start, and `intent` when it came through the launcher's assist entry (phones that start an activity for the assistant): any installed app can start that one too, so never treat `intent` as proof that the user asked, and do nothing sensitive on it without the user's own tap. You get no screen content and no voice; listen with `speech.recognize` (capability `speech.recognize`) if you need it. While the launcher is the assistant, Android also makes it the phone's default speech recognizer: it hands every request on to another installed recognizer, so speech to text keeps working in other apps (that needs the launcher's own microphone permission). Revoking the grant or removing the app turns the launcher's assistant off, and Android goes back to another assistant; the user can also pick another one under Default apps.
- call screening (`calls.screen`, SPECIAL, one app at a time: the user grants it from the app's card on the dashboard; if Deft is not the phone app, the same sheet asks Android to make it the caller ID and spam app, and until then no calls arrive): before an incoming call rings, the app gets `calls.screening` `{callId, number, verified, direction}`: `number` is the caller's number only when the app also holds `calllog.read` or `contacts.read` (else `null`; also `null` when the caller hides it), `verified` is true when the network vouched for the number (STIR/SHAKEN passed), `direction` is always `incoming` (outgoing calls are not sent). Answer with `calls.screenRespond` `{callId, action, skipLog?, skipNotification?}` (`action` `allow`, `silence` (rings without sound) or `reject`; `skipLog` and `skipNotification` are booleans, only with `reject`: leave the call out of the call log, or show no missed-call notification) → `{applied}`. The answer must come within 4 seconds of the call; after that, or with no answer, the call rings as usual and `applied` is `false` (also for an unknown or already answered `callId`). The event arrives live when the app is open (never queued); when it is closed, a background run with the trigger `screening` gets the same payload (declare `"screening"` in `background.triggers` and hold `background`; such a trigger waits ahead of others, joins a run already going as one more `background.trigger`, and is dropped once 4 seconds are up). `calls.screenRespond` works from background runs. Emergency numbers are never sent to the app. Each decision is in the audit log (the action, how long it took, whether it was verified; never the number). Revoking the grant or removing the app turns the launcher's call screening off.
